# Agent架构

本文说明一次用户请求如何成为工具调用和回复，以及哪些行为由程序控制。本项目是本地单Agent，不依赖多Agent或通用图执行框架。

## 执行顺序

1. 界面提交消息，SQLite事务递增需求版本，使旧任务失效。真实BOSS模式会先检查已有登录。
2. `requirements.py` 将模型提出的需求变更编译为带用户原话的结构。背景、岗位条件和交付要求分开保存，未提及条件保留。
3. `engine.py` 根据已有数据、未核验候选和剩余额度生成合法动作。唯一动作由程序确定；需要选择时，`reasoning.py`只允许模型填写受约束编号和参数。
4. 搜索前独立核查职责方向；`BossCDP`、`TencentCareers`或`Snapshot`只提供检索和详情。模型不能执行任意浏览器命令。
5. 原始岗位数据与匹配判断分开保存。明确城市、薪资等由规则比较，语义条件由模型分析；引用必须能在原文中找到，缺信息保持未知。
6. 模型组织候选优势、顾虑与建议，程序再次检查岗位身份、引用及任务版本，再发布到聊天和岗位面板。

## 状态与恢复

`State`保存当前需求、背景、岗位引用和历史清单。每个完成步骤保存`Checkpoint`，包含行动进度和已用额度。新消息产生新版本，旧模型或工具响应不能覆盖新状态。编号引用已经发布的清单，不引用临时搜索顺序。

暂停在步骤边界生效，不能取消已发出的请求。异常时明确失败或暂停，保留可恢复检查点。外部调用成功但检查点未写入时进程崩溃，恢复可能重复一次只读调用；不承诺任意执行点恢复。

## 模型与程序的边界

模型理解语义、提出选择和解释证据；程序限制工具范围、参数、任务版本和步数、时间、金额预算。非法结构做有限纠正，不能无限重试，也不能为了结果数量放宽用户条件。

引用存在性检查不等于语义正确。职责审核也依赖模型，可能误拒或漏拒。界面展示的是来源中的证据和当前核验结论，不是客观匹配百分数或录用保证。

## 实现入口

- `models.py`：数据结构与校验。
- `requirements.py`：需求变更、原话依据与历史指代。
- `engine.py`：合法动作、执行循环和发布控制。
- `reasoning.py`：兼容API、结构化输出、分析与交付。
- `store.py`：SQLite事务、岗位快照、检查点和预算账本。
- `boss_cdp.py`、`cdp_worker.py`、`tencent.py`、`providers.py`：只读岗位接入。
- `ui.py`、`ui_layout.py`、`ui_style.py`：会话、聊天、岗位面板与配置引导。
